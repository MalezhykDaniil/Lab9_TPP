# LeaderBoard

## Опис проєкту

LeaderBoard — це програмна система для моделювання результатів автомобільних перегонів та формування загального рейтингу учасників.

Програма дозволяє створювати перегони зі списком водіїв, визначати їхні позиції, нараховувати очки відповідно до обраної системи та формувати загальний рейтинг на основі результатів декількох перегонів.

Основні можливості:
- створення перегонів та визначення їхніх учасників;
- перевірка коректності вхідних даних;
- визначення позиції водія в перегонах;
- використання різних систем нарахування очок;
- накопичення очок за результатами декількох перегонів;
- формування рейтингу водіїв із сортуванням за кількістю очок;
- підтримка спеціалізованих типів учасників, зокрема автономних автомобілів.

## Архітектура проєкту

Клас `Leaderboard` відповідає за формування загального рейтингу водіїв на основі результатів декількох перегонів. Він зберігає список об'єктів `Race` та надає методи для обчислення сумарної кількості очок і формування впорядкованого рейтингу.

Метод `driverResults()` проходить по всіх перегонах, отримує очки кожного водія та накопичує їх у контейнері `std::map`. Для визначення унікальності та порядку водіїв використовується компаратор `DriverComparator`.

Метод `driverRankings()` формує вектор результатів і сортує його за кількістю очок у порядку спадання. Якщо декілька водіїв мають однакову кількість очок, додаткове сортування виконується за іменем і країною.

### Race

Клас `Race` представляє окремі перегони. Він зберігає назву перегонів, список учасників та об'єкт системи нарахування очок. Клас відповідає за перевірку коректності учасників, визначення позицій водіїв і отримання відповідної кількості очок.

### Driver

Клас `Driver` представляє учасника перегонів. Він зберігає ім'я та країну водія, визначає правила порівняння об'єктів і надає метод `displayName()` для отримання відображуваного імені. Похідні класи можуть перевизначати цей метод.

### Системи нарахування очок

Інтерфейс `IPointsSystem` визначає спільний контракт для систем нарахування очок. Класи `PointsSystem` та `AlternativePointsSystem` реалізують різні правила нарахування, що дозволяє змінювати систему без модифікації класу `Race`.

### SelfDrivingCar

Клас `SelfDrivingCar` є похідним від `Driver` та представляє автономний автомобіль як учасника перегонів. Він розширює базовий клас додатковим атрибутом — версією алгоритму автономного керування.

Методи `getAlgorithmVersion()` і `setAlgorithmVersion()` забезпечують отримання та зміну версії алгоритму. Метод `displayName()` перевизначає віртуальний метод базового класу `Driver`, завдяки чому автономний автомобіль може мати власний формат відображуваного імені.

Цей клас демонструє використання наслідування та поліморфізму в C++.

## Реалізація принципів SOLID

### S — Single Responsibility Principle (принцип єдиної відповідальності)

Кожен клас має окрему зону відповідальності:

- `Driver` зберігає інформацію про водія та визначає його ідентичність.
- `SelfDrivingCar` розширює функціональність водія для представлення автономного автомобіля.
- `Race` відповідає за зберігання результатів окремих перегонів, визначення позицій та нарахування очок.
- `PointsSystem` і `AlternativePointsSystem` реалізують правила нарахування очок.
- `Leaderboard` обчислює загальні результати та формує рейтинг водіїв.

### O — Open/Closed Principle (принцип відкритості/закритості)

Система підтримує розширення без необхідності змінювати вже реалізовану логіку. Наприклад, для додавання нової системи нарахування очок достатньо створити клас, який реалізує інтерфейс `IPointsSystem`. Клас `Race` працюватиме з новою реалізацією без зміни власного коду.

Також клас `SelfDrivingCar` розширює можливості `Driver` через наслідування та перевизначення віртуального методу `displayName()`.

### L — Liskov Substitution Principle (принцип підстановки Барбари Лісков)

Похідний клас `SelfDrivingCar` може використовуватися замість базового класу `Driver`, зберігаючи очікувану поведінку програми. Зокрема, автономний автомобіль може бути учасником перегонів і використовуватися методами, які працюють із водіями.

Реалізації `IPointsSystem` також дотримуються спільного контракту: обидві системи приймають позицію та повертають відповідну кількість очок, а для некоректної позиції повідомляють про помилку.

### I — Interface Segregation Principle (принцип розділення інтерфейсу)

Інтерфейс `IPointsSystem` містить лише один метод — `pointsForPosition()`. Завдяки цьому класи, які реалізують інтерфейс, не повинні реалізовувати непотрібні їм методи.

### D — Dependency Inversion Principle (принцип інверсії залежностей)

Клас `Race` залежить від абстракції `IPointsSystem`, а не від конкретної реалізації `PointsSystem`. Об'єкт системи нарахування очок передається через конструктор, що дозволяє використовувати різні реалізації без зміни класу `Race`.

## Тестування

Для перевірки коректності роботи програми використовується бібліотека **GoogleTest**. Тести охоплюють основні класи системи, перевіряють правильність обчислень, обробку помилок і взаємодію між компонентами.

### PointsSystem та AlternativePointsSystem

Перевіряється правильність нарахування очок залежно від позиції учасника. Також тестуються некоректні значення позицій та поведінка обох реалізацій інтерфейсу `IPointsSystem`.

### Race

Тести перевіряють:
- створення перегонів із коректними учасниками;
- визначення позиції водія;
- правильність нарахування очок;
- обробку порожнього списку учасників і нульових вказівників;
- відхилення повторного додавання одного водія;
- можливість використання альтернативної системи нарахування очок;
- роботу з похідним класом `SelfDrivingCar`;
- коректність копіювання об'єкта та часу життя залежностей.

### Leaderboard

Перевіряється:
- накопичення очок за декілька перегонів;
- правильність формування загальних результатів;
- сортування рейтингу за кількістю очок;
- порядок водіїв за однакової кількості очок;
- розрізнення водіїв з однаковими іменами, але різними країнами;
- робота з порожнім списком перегонів;
- коректність копіювання об'єкта та збереження його працездатності після знищення початкових об'єктів.

### Результати тестування

Усі реалізовані автоматизовані тести завершилися успішно. Це підтверджує коректність основної функціональності програми, обробки передбачених помилкових ситуацій та взаємодії між її компонентами.

## Технології

Для розробки проєкту використано такі технології та засоби:

- **C++20** — основна мова програмування та стандарт мови.
- **CMake** — система конфігурації та збирання проєкту.
- **GoogleTest** — бібліотека для написання та виконання автоматизованих тестів.
- **STL** — стандартна бібліотека C++, зокрема контейнери `std::list`, `std::map`, `std::vector`, `std::unordered_set` та засоби роботи зі смарт-вказівниками.

## Збирання та запуск

Для збирання проєкту використовується CMake. Перед збиранням необхідно переконатися, що GoogleTest доступний для CMake.

Відкрити термінал у кореневій директорії проєкту та виконати команди:

```bash
cmake -S . -B build
cmake --build build
```

Для запуску автоматизованих тестів через CTest:

```bash
ctest --test-dir build --output-on-failure
```

Тестова ціль `LeaderBoard_Test` збирається окремо та використовує бібліотеку `LeaderBoard` і GoogleTest. Функція `gtest_discover_tests()` забезпечує автоматичне виявлення тестових випадків для CTest.


### Призначення каталогів

- `include/` — заголовкові файли з оголошеннями класів, інтерфейсів та структур.
- `source/` — файли реалізації методів і логіки роботи класів.
- `tests/` — модульні тести, створені за допомогою GoogleTest.

Файл `CMakeLists.txt` у кореневому каталозі містить налаштування проєкту, створення бібліотеки та підключення тестування. Файл `tests/CMakeLists.txt` відповідає за створення тестової програми та її інтеграцію з CTest.
